# 백로그

아직 하지 않은 것과 아직 정하지 않은 것만 둔다.
지금 참인 상태는 `PROGRESS.md`, 지나간 경위는 `CHANGELOG.md`에 있다.

## 미결 결정

### 이 프로젝트를 계속할 것인가

무료·오픈소스라는 전제(`PROGRESS.md` 「프로젝트 전제」)가 당사자에게 실제로 의미 있는지
확인되지 않았다. 확인되지 않으면 만들 이유가 약하다. 웹앱 1차본은 이 질문에 답을 만들려고
내놓는 것이다.

### 당사자 검증을 어떻게 할 것인가

조사가 짚은 빈 곳은 전부 검색 기반 추론이다. 특히 "프라이버시 우려"는 조사자가 추정한
것이지 당사자가 말한 것이 아니다. 누구에게 어떤 방식으로 물을지 정하지 않았다.

### 화자 전환을 화면에 어떻게 표시할 것인가

웹앱 1차본에서는 **라벨 없이 문단만 나누는 것으로 정했다.** 브라우저 내장 Web Speech API가
화자 정보를 주지 않아 선택지가 하나뿐이었기 때문이지, 화면 설계의 답을 찾아서가 아니다.
화자 정보를 실제로 주는 경로(iOS 네이티브, 셀프호스팅 서버, 온라인 화자분리 엔진)를 붙이면
이 질문은 다시 열린다. 라벨을 붙일지, 색만 바꿀지, 문단 간격만 둘지.

## 남은 검증 과제

### 실행 중인 웹 경로

- **모바일 Safari의 간헐적 `audio-capture` 고장을 재현·감지하는 방법.** 정상 종료된 인식의
  재연결은 2026-09-10에 통과했지만, 앞서 관찰한 "재시작은 되는데 마이크 입력이 돌아오지 않는"
  상태는 재현하지 못했다. `audiostart`만으로는 복구를 판정할 수 없다는 것까지가 지금 아는 전부다.
  운영 위험으로 계속 추적한다.
- **한국어 온디바이스 팩을 실제로 `install()`해서 인식 품질·지연 측정.** 지금은 데스크톱
  Chrome에서 "내려받을 수 있다"(`downloadable`)까지만 확인했다.

### iOS 단계에 들어가면

- **Apple 음성 인식의 한국어 실시간 품질 미측정.** 구형 `SFSpeechRecognizer`와 iOS 26+
  `SpeechAnalyzer` 어느 쪽도 직접 재 본 적이 없다. iOS 단계에 들어가면 1순위다.
- **`SFSpeechRecognizer`의 서버 폴백 여부를 실측으로 확정.** 문서가 아니라 측정으로 확인하고,
  확정하지 못하면 그 API를 쓰지 않는다(`PROGRESS.md` 「온디바이스 범위」 설계 제약 3).

### 엔진 선택지

이 절의 후보는 **1차본에서 쓰지 않는다.** 웹에서 쓰려면 셀프호스팅 서버가 필요한데 1차본은
서버를 두지 않기로 확정했다. 포크하는 사람과 iOS 경로에서 의미가 있다.

- WhisperLiveKit + 한국어 파인튜닝 Whisper 조합의 실제 지연·정확도 미측정.
- Streaming Sortformer / diart의 한국어 화자분리 정확도 미측정. 같은 픽스처로 상용 API와
  비교할 수 있다.
- sherpa-onnx 한국어 스트리밍 모델의 빈 결과 버그 재현 여부.

### 사용자·경쟁자

- **청각장애인 발화 인식률은 어떤 엔진으로도 측정한 적이 없다.** 검증하려면 당사자 음성이 필요하다.
- 소보로 플러스 직접 사용 평가(경쟁자 실물 확인).
- 실녹음 검증이 5분 1건뿐이다. 잡음·거리·겹침 조건을 넓혀야 한다.

## 진단 정보 복사 (2026-09-13 위원장 승인, 미착수)

**왜 필요한가**: 요청자가 배포본에서 "자주 연결이 끊긴다"를 첫 결함으로 지적했는데
(`PROGRESS.md` 알려진 한계), 어떤 기기에서 어떤 간격으로 끊기는지 알 방법이 없다.
끊김 간격이 40초에 규칙적으로 몰리면 원인이 좁혀지고, 흩어져 있으면 다른 원인이다.

**왜 A안인가**(자동 수집 아님): 사용자가 아직 한 명이라 지금 필요한 것은 통계가 아니라
그 한 사람의 끊김 원인이다. 자동 수집 인프라를 세우는 비용이 얻는 정보보다 크고,
**서버 0 원칙**을 깨야 한다. 사용자가 직접 복사해 보내는 방식은 그 행위 자체가 동의라
단말기 정보 수집의 법적 문제도 없다.

**B안(서버리스 자동 수집)으로 갈 조건**: 사용자가 수십 명을 넘고 개별 제보로 패턴이
안 보일 때. 그때는 서버 0 원칙을 깨는 판단을 정면으로 해야 하므로 별도 설계 논의 대상이다.

### 설계

정지 후 나타나는 컨트롤에 **「진단 정보 복사」** 버튼 하나를 더한다. 복사 형식 예시:

```
말동무 진단 2026-09-13
세션 4분 12초 · 확정 37건
끊김 6회 (간격 40.1s 40.3s 39.8s 41.0s 40.2s 39.9s)
복구 성공 6 / 실패 0 · 최대 공백 5.2초
오류: aborted 6, no-speech 2
브라우저: Safari 26.6 · iPhone · 화면 390x844 · 홈화면앱 예
글자 크기 34px · 온디바이스 가능 여부: 미지원
```

⚠ **발화 내용은 한 글자도 담지 않는다.** 확정 결과는 건수만 센다. 이 규칙을 어기면
「테스트 음원 취급 규칙」과 같은 선을 넘는다.

### 담을 항목

- 세션 길이, 확정 결과 **건수**(내용 아님)
- 끊김 횟수와 **간격 나열**(원인 판별의 핵심), 복구 성공·실패 수, 최대 공백
- 오류 `kind`별 빈도
- User-Agent에서 뽑은 브라우저·OS·기기, 화면 크기, `display-mode: standalone` 여부
- 글자 크기 설정, `SpeechRecognition.available()` 결과(있으면)

### 구현

`web/diagnostics.js`를 새로 만들고 `app.js`가 인식 사건을 그쪽에도 흘린다.
`recognition.js`·`captions.js`는 건드리지 않는다(계약 유지).

**재사용**: `spike/web/index.html`이 이미 같은 구조다. 세션 통계(`stats` 객체: ends,
restarts, maxGap, finals, errors, silences, restartAttemptFailures)를 쌓고 「로그 복사」로
내보낸다. 그때 아이폰 실측을 이 방식으로 받았으므로 형식이 검증돼 있다.

**테스트**: 순수 함수(사건 → 통계 → 문자열)라 `node --test`로 전부 검증한다.
특히 **발화 내용이 절대 섞이지 않는다**는 것을 테스트로 못 박는다.

## STT 엔진 eval 하네스 (2026-09-13 착수 결정, 미착수)

**왜 필요한가**: 상용 엔진을 "고급 엔진" 선택 경로에 올릴 때 어느 것을 올릴지 판정할 근거가
없다. 지금 가진 수치는 조건이 제각각이라 비교가 성립하지 않는다(우리 실측은 합성 음원,
국내 수치는 리턴제로 자사 벤치마크).

**절차 정본**: `llm-model-eval` 스킬. 0단계(`PORTS.md` 확인) 결과 **STT eval 판정은 없다**
(2026-09-13 확인, 전부 Gemini LLM 판정). 새로 만들되 케이스 스키마·리포트 형식·측정 규칙은
그 스킬을 따른다.

### 재사용할 자산 (새로 만들지 말 것)

- `spike/probe.py` 실시간 WebSocket 프로빙, `spike/score.py` CER 채점, `ground_truth_*.json` 스키마
- `speech-toolkit/STT/` 배치 STT 7종(**다글로 포함**). 리턴제로·CLOVA는 없어 새로 붙여야 한다
- gildongmu `src/__ab__/` 하네스 구조

### 정답 전사 (2026-09-13 위원장 판정)

**공개 한국어 데이터셋 + 장교조 회의 녹음(속기록 보유분)** 두 갈래로 간다.

- **공개 데이터셋**: 재현 가능한 기준선. 저장소에 넣거나 내려받는 스크립트를 둔다.
- **장교조 회의 + 속기록**: 실제 조건 검증. 속기록이 이미 정답이라 만드는 노동이 없다.
  ⚠ 음성·전사는 **저장소에 넣지 않는다**(테스트 음원 취급 규칙). 경로를 환경변수로 받는다.

⚠ **착수 전에 확인할 것 둘.**

1. **속기록이 축어록인가.** 요약·정리형이면 CER을 잴 수 없다. "어" 같은 간투사와 반복까지
   그대로 적힌 축어록이어야 문자 단위 대조가 성립한다. 정리형이면 그 파일로는 지연과
   화자 전환만 재고 정확도는 다른 샘플로 잰다.
2. **회의 음성을 외부 API에 보내도 되는가.** eval은 음성을 리턴제로·CLOVA·Deepgram 서버로
   올린다는 뜻이다. 노조 회의 내용이 외부 사업자에게 전송되므로 참석자 동의 범위를
   위원장이 판정해야 한다. 안 되면 공개 데이터셋만 쓴다.

### eval의 범위: 상용 API끼리의 우선순위 (2026-09-13 위원장 판정)

**브라우저 내장 엔진은 eval 대상이 아니다.** 과금이 없어 **어느 사용자나 쓸 수 있는 기본
자산**이므로 없앨 수도 바꿀 수도 없다. 하이브리드 구조에서 기본 경로는 그대로 남고 상용은
그 위에 얹는 선택지다. 따라서 판정 질문은 "기본을 상용으로 바꿀까"가 아니라
**"선택 경로에 어느 상용을 먼저 붙일까"**다.

이 판정이 하네스를 크게 단순화한다. 가상 오디오 장치도 브라우저 자동화도 필요 없고,
같은 음원을 상용 API 여럿에 흘려 CER·지연·화자 전환을 나란히 재면 된다.
`spike/probe.py`와 `speech-toolkit/STT/`가 그대로 그 모양이다.

갱신 2026-09-13: "기준선(브라우저 엔진)을 못 재서 판정의 뿌리가 비어 있다"에서
"기본 엔진은 비교 대상이 아니라 전제"로.

### 기존 지연 수치의 한계

`llm-model-eval` 측정 규칙 1: **지연은 다른 날 최소 2회 재현해야 판정 근거가 된다.**
우리 스파이크는 각 조건을 한 번씩만 쟀으므로 "Muse가 Deepgram보다 빠르다"는 결론이
그날의 서빙 상태일 수 있다. eval을 세울 때 다른 날 재측정을 포함한다.

## 뒤집힌 결정

폐기한 판단과 그 근거를 남긴다. 같은 자리에서 같은 오류를 반복하지 않기 위한 기록이다.

- ~~프로바이더 1순위는 Meta Muse~~ → **폐기.** 무료 배포가 전제로 확정되면서 종량 과금
  클라우드 API는 구조적으로 부적합해졌다. 온디바이스가 기본선이다.
- ~~씨사운드는 화자 분리를 지원하지 않는 1:1 대면용 하드웨어~~ → **틀렸다**(2026-09-05).
  앱 단독으로 동작하고 8인 회의에서 실시간 화자 분리가 실용 수준으로 작동한다.
  홍보 문구에 없다는 것을 기능이 없다는 근거로 삼은 오류였다.
- ~~온디바이스의 근거는 프라이버시~~ → **비용이 1차 근거이고 프라이버시는 부수 효과.**
- ~~실시간 화자 분리는 스트리밍의 구조적 한계~~ → **과잉 일반화였다.** 상용 API 구현의
  문제이고, diart·NVIDIA Streaming Sortformer 같은 온라인 전용 알고리즘은 실제로 동작한다.
  (speech-toolkit 공개 문서에도 정정 반영해 푸시함)
