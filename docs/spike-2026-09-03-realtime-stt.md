# 실시간 한국어 다화자 전사 스파이크 결과 (2026-09-03)

목적: 청각장애인용 실시간 캡션 스킬을 만들기 전에, 한국어 실시간 전사와 실시간 화자 분리가
실제로 성립하는지 실측으로 확인한다.

## 테스트 조건

- 음원: Gemini TTS로 합성한 한국어 3화자 회의 대화(Kore·Puck·Charon), 12턴
- 정답 전사문·화자·턴 경계 시각을 확정한 픽스처(`ground_truth.json`)
- 턴 간격 400ms 판과 900ms 판 두 조건
- 오디오를 1배속으로 페이싱해 WebSocket으로 흘리고 도착 이벤트마다 경과 시각 기록
- 두 프로바이더 모두 raw WebSocket 사용(SDK 버퍼링이 측정에 섞이지 않게)

## 1. 문서 조사로 먼저 걸러진 것

| 프로바이더 | 실시간 | 실시간 화자 분리 | 세션 상한 |
|---|---|---|---|
| Meta Muse Voice Transcribe | 지원 | DIARIZATION 모드 | 60분 |
| Deepgram nova-3 | 지원 | `diarize=true` | 사실상 없음 |
| Gemini 3.5 Transcribe Live | 지원 | **공식 미지원** | **10분** |
| ElevenLabs Scribe v2 Realtime | 지원(~150ms 주장) | **미지원** | 미확인 |

Gemini Live는 공식 문서가 "Speaker diarization is not supported in live streaming sessions"라고
명시하고 세션이 10분이라 회의용 캡션에 부적합하다. ElevenLabs도 실시간 화자 분리가 없다.
따라서 다화자 실시간 캡션의 실측 후보는 Muse와 Deepgram 둘뿐이다.

## 2. 지연·정확도 실측

| 지표 | Muse | Deepgram |
|---|---|---|
| partial 지연 중앙값 | **140~158 ms** | 304~308 ms |
| partial 지연 p90 | **160~178 ms** | 484~493 ms |
| 확정 지연 중앙값 | 650~674 ms | **475~476 ms** |
| 확정 지연 최대 | **683~714 ms** | 896~2,107 ms |
| 문자오류율 CER | **1.09~1.82%** | 1.45~2.18% |

읽는 사람이 체감하는 것은 partial 지연이다. Muse가 두 배 빠르고, 무엇보다 p90이 중앙값과
20ms 차이로 붙어 있어 흔들림이 없다. Deepgram은 확정을 median으로는 더 빨리 내지만 꼬리가
2.1초까지 튄다. 캡션에서 2초 정지는 대화를 놓치는 길이다.

전사 정확도는 둘 다 실용 수준이다. 오류는 동음이의 고유명사에 몰렸다(`지필 평가`→`집필 평가`,
`동아출판`→`동화 출판`). 이런 오류는 keyterm 바이어싱으로 줄일 여지가 있다(양쪽 다 지원).

## 3. 화자 분리: 제품의 기둥으로 삼을 수 없다

| 조건 | Muse | Deepgram |
|---|---|---|
| 턴 간격 400ms | 2명 | 2명 |
| 턴 간격 900ms | **3명** | **1명** |
| (대조군) Muse 배치 DIARIZATION | 3명 | 해당 없음 |

정답은 3명이다. 결과는 불안정하고, 두 프로바이더가 **서로 반대 방향으로** 움직였다.
간격을 늘리자 Muse는 3명을 찾았고 Deepgram은 오히려 전부 한 사람으로 뭉갰다.

**합성 음성 탓이라는 가설은 배제됐다.** 같은 파일·같은 모델·같은 DIARIZATION 모드로
Muse 배치 엔드포인트를 돌리자 화자 3명이 나왔다. 모델은 이 세 목소리를 구분할 수 있고,
스트리밍에서만 못 한다. 미래 구간을 못 보는 스트리밍 클러스터링의 구조적 한계다.

### 턴 경계도 신뢰할 수 없다

정답 12턴에 대해 Muse는 7개 세그먼트로 뭉쳤고(인접한 다른 화자의 발화를 한 덩어리로 병합),
Deepgram은 23개로 잘게 쪼갰다. 두 조건 모두에서 같은 경향이 나왔다.
Muse 배치조차 12턴을 8개로 병합했다.

## 4. 설계에 반영해야 할 결론

1. **1순위 프로바이더는 Muse다.** 지연·안정성·정확도·세션 길이(60분) 전부 우세하고,
   실시간 화자 분리가 실측으로 한 번이라도 성립한 유일한 사례다.
2. **화자 라벨을 화면 구조의 기둥으로 삼지 않는다.** 화자별 말풍선·화자별 열 같은 UI는
   라벨이 틀리는 순간 읽는 사람을 오도한다. 라벨은 보조 표시로 두고 끌 수 있게 한다.
3. **턴 경계도 신뢰하지 않는다.** 확정 텍스트가 연속으로 흐르고 partial이 꼬리에 붙는
   단일 흐름이 가장 안전한 화면 구조다.
4. **Deepgram은 한국어 실시간 화자 분리에 쓰지 않는다.** 폴백으로 쓰더라도 라벨 없이 쓴다.
5. **Gemini Live는 회의용에서 제외한다.** 10분 세션 상한이 회의 길이와 맞지 않는다.

## 5. 실제 회의 녹음 재검증

실제 다화자 한국어 회의 녹음 앞 5분으로 재측정했다(참석자 다수, 겹침·잡음 포함).
**녹음 내용은 이 문서에 남기지 않으며 집계 수치만 기록한다.**

| 지표 | Muse 스트리밍 | Deepgram 스트리밍 |
|---|---|---|
| partial 지연 중앙값 | **151 ms** | 317 ms |
| partial 지연 p90 | **169 ms** | 512 ms |
| partial 지연 최대 | **208 ms** | **2,322 ms** |
| 확정 지연 중앙값 | 670 ms | 476 ms |
| 확정 지연 최대 | **708 ms** | 2,322 ms |
| 확정 세그먼트 | 52개 | 84개 |
| 구분된 화자 | 3명 | 3명 |

대조군: Muse 배치 4명 / 44세그먼트. 별도 상용 전사(클로바노트) 기준 이 구간에 7명.

### 두 가지가 확정됐다

1. **지연 특성은 합성·실녹음에서 동일하다.** Muse는 151ms에 최대 208ms로 흔들림이 없고,
   Deepgram은 중앙값은 쓸 만하나 최대 2.3초까지 튄다. 합성 음원에서 본 꼬리 문제가
   실제 녹음에서 그대로 재현됐다. 캡션 품질에서 이 차이가 결정적이다.
2. **화자 수는 계통적으로 과소 계수된다.** 스트리밍 3명 < 배치 4명 < 클로바노트 7명으로,
   미래 구간을 볼 수 있는 정도에 정확히 비례해 정렬됐다. 두 프로바이더가 독립적으로 3명에
   수렴한 것은 정답이라기보다 스트리밍 클러스터링의 천장으로 보인다.

### 반대로 뒤집힌 것: 턴 경계는 실녹음에서 쓸 만하다

합성 픽스처에서는 12턴을 7개로 뭉쳤지만, 실녹음 5분에서는 52개 세그먼트가 나왔다
(클로바노트 발화 밀도로 환산한 기대치 약 33개와 같은 자릿수). 인위적인 400ms 균일 간격이
엔드포인팅을 방해했던 것이고, 자연스러운 대화의 쉼에서는 턴 분절이 정상 작동한다.
Muse는 세그먼트 52개에 화자 전환 이벤트 52회로 모든 세그먼트에 전환 신호가 붙었다.

**즉 "화자가 바뀌었다"는 신호는 쓸 수 있고, "누구인지"는 쓸 수 없다.** 이 비대칭이
화면 설계의 핵심 근거다.

## 6. 이 스파이크가 답하지 못한 것

- **ElevenLabs Scribe v2 Realtime 지연은 측정하지 않았다.** 실시간 화자 분리가 없어
  후보에서 빠졌고, 문서상 ~150ms 주장은 Muse 실측치(151ms)와 같은 수준이다.
- **Deepgram 파라미터 튜닝을 하지 않았다.** `diarize=true` 기본 조합 한 벌만 시험했다.
- **참조 화자 수 7명 자체가 추정치다.** 클로바노트도 완벽하지 않다. 다만 스트리밍·배치·
  클로바노트가 3 < 4 < 7로 정렬된 방향성은 세 방법의 lookahead 차이와 일치한다.

## 부록: Muse 실시간 WebSocket 프로토콜 (실호출로 확인)

- 엔드포인트 `wss://api.meta.ai/v1/asr/realtime`
- **인증은 핸드셰이크 첫 JSON 프레임으로 보낸다. `Authorization` 헤더는 무시된다.**
- 첫 프레임: `{"authorization":{"accessToken":"Bearer <KEY>"}, "audioEncoding":"PCM_24KHZ",
  "model":"muse-voice-transcribe-1.0", "mode":"DIARIZATION", "partialMode":"CUMULATIVE",
  "languageBias":["Korean"], "emitAudioProgress":true}` → 서버가 `{"sessionId":"..."}` 응답
- 오디오는 컨테이너 없는 raw PCM(s16le mono)을 바이너리 프레임으로. 80ms 청크, 실시간 페이싱.
  **5초 이상 앞질러 보내면 안 된다.**
- 응답 이벤트: `speechStart` / `transcript{transcript, final, audioProcessedMs}` /
  `speechEnd` / `speechComplete{transcript}` / `speaker{label}` / `audioProgress` / `error`
- `speaker` 이벤트는 **그 뒤가 아니라 앞의 오디오**에 라벨을 붙이며 발화 경계를 뜻하지 않는다
- 종료는 `{"type":"endStream"}` 전송 후 close code 1000까지 수신 계속
- 한도: 테넌트당 동시 8스트림, 시간당 1,000스트림, $0.18/오디오 시간
